# KayaGo · 围棋 AI 对弈

一个**开源、零第三方依赖**的 Android 围棋应用，内置**从零实现的蒙特卡洛树搜索（MCTS）AI**。
不联网、不加载任何权重文件，装上就能下。

> 榧（kaya）是传统日本棋盘的用材，项目名由此而来。

---

## 下载安装

到本仓库的 [Releases](../../releases) 页面下载 `KayaGo-1.2.0.apk`，手机上打开安装即可
（需要允许「安装未知来源应用」）。

- 最低系统：Android 8.0（API 26）

- 安装包体积：约 70 KB

## 棋力说明（请先读）

本项目的 AI 是**从零手写的传统 MCTS 引擎**，没有神经网络、没有人类棋谱训练、没有权重文件。
请对棋力有合理预期：

- **9 路**：大约相当于业余级位水平——初学者到入门爱好者可以一战。
- **13 / 19 路**：搜索空间大得多、推演更短，棋力明显弱于 9 路，适合休闲对弈。
- 它**不是** KataGo / Leela Zero 那种职业级引擎，本项目也不追求那条技术路线。
  如果你要的是「最强」，请直接使用 KataGo。

引擎擅长的事情：吃子、打吃逃跑、做眼/破眼的基本判断、局部应手、开局占角、
收官时不去填自己的空。
不擅长：大规模全局战斗、精确的形势判断、复杂的劫争转换。

> 想让它更强：直接调高「AI 棋力」档位（思考时间越长越强）。

## 技术实现

### 1. 规则内核 `com.kayago.game`

- **`Board`**：棋盘状态 + 增量维护的棋块结构。
  - 坐标用「带边框」内部索引，边界统一为 `WALL`，省掉所有越界判断。
  - 棋块用**单向链表**表示，链头索引即棋块 id；气数用「时间戳去重」统计，
    落子 / 撤销都在 O(棋块大小) 量级。
  - 提子时相邻敌块气数直接 **-1**（落子点原本就是它们的口气），避免反复全量扫描；
    只有自己这块棋在落子后重算一次气数。
  - 撤销时需要处理「接点被摘掉导致棋块裂开」的问题：只有在落子时**合并了 2 块以上**
    己方棋的情况下才做一次连通性检查，必要时按相邻关系局部重建棋块。
  - **位置超级劫**：用开放寻址的长整型哈希集合记录本局出现过的所有局面，
    既保证规则正确，也让 AI 在搜索中不会提出重复局面的着法。
- **`Scorer`**：中国规则数子（子 + 空），并输出每个空点的归属图供界面显示。
- **`Game`**：对局流程、历史、终局判定、认输。

### 2. AI 引擎 `com.kayago.ai`

- **共享树多线程 UCT**：节点访问数 / 胜场用原子量维护，选择时叠加 virtual loss 降低线程撞车。
- **根节点 PUCT + 启发式先验**（棋力关键）：纯 UCT 在空盘、稀疏局面下胜率几乎是纯噪声，
  引擎会随手走废棋。这里先把每个合法点做一次棋理打分（提子、救棋、自紧气、连络、
  线位、与前手距离、角部常见着点……），再用 softmax 变成先验分布，按
  `Q + c·P·√N/(1+n)` 选择。开局因此会自然地占角（三三/星位），而不是贴着边线乱走。
- **根节点 RAVE / AMAF**：把「本局快速推演里出现过、且落在窗口内」的着法也算作一次访问，
  用 `β = √(k/(3n+k))` 与树内胜率混合。访问次数还很少时，这个信号比树内胜率可靠得多。
- **轻量推演策略**：一次邻居扫描完成大部分判断——能提就提、被打吃就逃、
  不填自己的眼、不自紧气、不往自己空里填、优先在上一手附近应。
- **终局**：双方连续停手或达到步数上限后，用中国规则数子判断胜负。
- **形势判断**：`estimateScore` 只做随机推演不建树，用来估算领先子数。

性能量级（开发机 JVM，单线程）：约 **0.5 ~ 1 万局随机推演/秒**（视局面而定），
`play + undo` 约 **150 万次/秒**。手机上按 CPU 核心数并行（最多 8 线程）。

仓库里还带了一个对局跑分工具 `tools/MatchRunner.java`：让同一套代码的两组搜索配置
互相对弈（每局交换黑白），用来客观检验某项改动到底有没有让引擎变强，而不是凭感觉。

### 3. 自对弈进化（RSI 式闭环）`tools/`

引擎的参数不是拍脑袋定的，也不靠人工反复手调，而是由一套自动循环不断进化出来的：

```
自对弈产数据  →  策略蒸馏训练  →  跑分验证  →  晋升为新冠军  →  回到第一步
```

- **产数据** `tools/SelfPlayData`：用现任冠军参数自我对弈，记录每个局面上引擎自己的
  **根访问分布**（它认为哪些点好、好到什么程度），并在每局开头补一行
  `RESULT <winner> <diff>`——这一局的**胜负**就是策略梯度的回报信号。
- **学习** `tools/Trainer`：把走子评估建模成「25 维特征 × 权重」的线性策略
  （`MoveFeatures`，训练与推理共用同一份特征定义，不会出现训练/上线不一致）。
  训练是**混合目标**：

  1. **策略蒸馏**：拟合引擎自己的根访问分布 `CE(p, 访问分布)`——只是「模仿自己」；
  2. **胜负策略梯度**：`-pgWeight · outcome · log p(实际走的那手)`，
     `outcome` 是该局面行棋方最终的胜负（赢 +1 / 输 -1）。这一项用的是**真实对局结果**，
     赢了就把当时那手往上抬、输了就往下压，是引擎自身先验之外的新信息。

  两个关键细节：**logit 与梯度都按推理温度缩放**（`1 / priorTemperature`；
  因为 `z = (Σw·f)/T`，所以 `∂z/∂w = f/T`，漏掉它更新步长会随温度被动放大；
  不缩放则最优解退化成 `w ≈ w_冠军 / T`，权重被整体压扁、先验越来越糊）；
  **L2 向冠军权重收缩**（proximal）而不是向 0 收缩，保证每轮都是小步精修。
- **闸门** `tools/Evolve`：候选先过「开局不变量」硬检查（空盘第一手不走一路/二路、
  落在角部一带），把「练废了」的候选直接挡在跑分之前。
- **验证** `tools/MatchRunner`：候选与现任冠军互相对弈，每局交换黑白。
  内置基线权重是**写死的常量**（`Tuned.BUILTIN_WEIGHTS`），不会跟着进化一起变，
  这样跑分永远是「现在 vs 最初」，而不是「自己打自己」。
- **晋升** `tools/Evolve`：用胜率的 **Wilson 95% 置信下界**是否过半来判定，
  而不是看原始胜率——样本小时原始胜率噪声极大（同一份候选，16 局里可能这轮 43.8%、
  下轮 62.5%），按下界判等价于要求「有 95% 把握更强」，证据不足就宁可不动。
  晋升后的冠军成为下一轮的数据来源——**更强的策略 → 更好的数据 → 更强的策略**。
- **第二条进化路径**：搜索超参邻域探测（puctC / 先验温度 / raveK …），同一套判据。

跑法：

```bash
# 2 轮进化，每轮自对弈 24 局（可以挂着跑很久，轮数/局数往上加就行）
java -cp /tmp/kayago-test tools.Evolve 2 24 60 9 16 0
# 单独验证当前参数 vs 内置手写基线（48 局、每手 150ms）
java -cp /tmp/kayago-test tools.MatchRunner 48 150 9
# 只改一个超参做对照，例如先验温度 14
java -cp /tmp/kayago-test tools.MatchRunner 40 150 9 0 100 14
```

产物是 `app/src/main/java/com/kayago/ai/TunedParams.java`（自动生成，别手改），
重新编译 APK 即生效。**每轮都必须以 95% 置信度跑赢上一轮才会被采纳**，所以不会越进化越差。

**1.2.0 的进化实测**（9 路，每轮自对弈 24 局、验证 16 局）：

| 轮次 | 候选 vs 冠军（16 局） | 判定 |
| --- | --- | --- |
| 第 1 轮 | 7 : 9（43.8%） | 下界未过半，拒绝 |
| 第 2 轮 | 10 : 6（62.5%） | 下界仍未过半，拒绝 |

> 补充跑分：把第 2 轮候选拉长到 **48 局**再和基线打，结果 **21 : 27（43.8%）**——
> 证明 16 局里的 62.5% 只是噪声。改用 Wilson 下界判据后这种候选会被直接拒绝。

**超参抽查**（40 局/档，150ms/手，基线 `T=9, puctC=1.6`）：

| 改动 | 结果 | 说明 |
| --- | --- | --- |
| 先验温度 3 | 6 : 14（30%） | 先验太尖，明显更差 |
| 先验温度 5 | 6 : 14（30%） | 同上 |
| 先验温度 14 | 13 : 16（45%） | 更平也没更好 |
| 先验温度 24 | 13 : 15（46%） | 更平也没更好 |
| puctC 1.0 | 8 : 14（36%） | 更差 |
| puctC 2.4 | 7 : 13（35%） | 更差 |

**加入胜负信号后的实测**（每轮自对弈 32 局，验证 32 局，60ms/手）：

| 训练目标 | 候选 vs 基线（32 局） | 判定 |
| --- | --- | --- |
| 蒸馏 + 胜负梯度（未做优势归零） | 10 : 22（31.3%） | 明显更差，拒绝 |
| 蒸馏 + 胜负梯度（按行棋方**优势归零**） | 14 : 18（43.8%） | 仍不如基线，拒绝 |

第二行验证了「去偏」的必要性：直接拿胜负当回报时，9 路白棋胜率高这件事会让所有白方局面
都吃正回报、黑方局面上都吃负回报，而特征里并没有颜色——等于在教一个自相矛盾的目标。
改成「减去本方平均回报」后，从 31.3% 回到 43.8%。

结论与坦白：

1. **当前交付的仍是最初的手写参数**。纯蒸馏不含新信息；加入胜负信号后方向是对的
   （去偏把胜率从 31% 拉回 44%），但在「25 维人工特征 + 线性策略 + 每轮几十局」这个
   算力档位上，信号仍被方差淹没，打不过已经调好的手写权重。
2. **这个闸门本身是有代价的**：Wilson 95% 下界在 32 局时要胜率约 **65%** 才放行。
   真实世界里这类方法的一步改进通常是几个百分点，所以在小样本下**根本不可能被证明**。
   想真正看到增益，必须把自对弈规模提到成千上万局，并引入**价值基线**（
   用「当前局面的估值」而不是「本方均值」做优势），而不是加大学习率。
3. 这套框架的价值恰恰在于**它诚实地拒绝了所有候选**——包括那个一度以 62.5%「胜出」、
   实际只是噪声的候选。**没有可验证的增益，就不发布参数改动。**



### 4. 界面 `com.kayago.ui`

- **`BoardView`**：完全自绘——木纹渐变棋盘、三层柔和阴影、立体棋子（径向渐变 + 投影 + 高光）、
  星位、坐标（跳过字母 I）、最后一手标记、待确认落点、AI 建议金环、归属标记；
  落子有 140ms 缩放淡入动画与触感反馈；处理两步确认落子。
- **`PlayerCardView`**：黑/白棋手卡片（立体棋子图标、我方/AI、执子、提子数），
  行棋方高亮，AI 思考时显示进度条。
- **`ActionButton`**：底部图标操作按钮（自绘 vector 图标 + 文字标签）。
- **`MainActivity`**：对局状态机、三个自定义对话框（新对局设置 / 形势判断 / 终局结算）、
  AI 后台线程与状态令牌。`onDraw` 内不做对象分配，着色器只在几何变化时重建。

## 自测

规则内核和 AI 都是纯 Java、零 Android 依赖，可以直接在电脑上跑：

```bash
javac -encoding UTF-8 -d /tmp/kayago-test \
  app/src/main/java/com/kayago/game/*.java \
  app/src/main/java/com/kayago/ai/*.java \
  tools/EngineSelfTest.java
java -cp /tmp/kayago-test tools.EngineSelfTest
```

覆盖 53 项断言：单子提子、禁止自杀、「先提子后有气」、
简单劫与位置超级劫、真假眼识别、数子与归属、随机落子 + 逆序撤销的一致性压力测试、
开局不乱走一路二路、形势判断方向、AI 能否吃掉被打吃的大龙、AI 自对弈完整性。

引擎改动是否真的变强，不看感觉看跑分：

```bash
java -cp /tmp/kayago-test tools.MatchRunner 48 150 9     # 每手 150ms，9 路，48 局
```

它让「当前 `TunedParams` 参数」对上「写死的初始手写基线」（每局交换黑白），
输出胜率与 Wilson 95% 下界。也可以用第 6、7 个参数只覆盖一个超参做对照：

```bash
java -cp /tmp/kayago-test tools.MatchRunner 40 150 9 0 100 3    # 先验温度改成 3
java -cp /tmp/kayago-test tools.MatchRunner 40 150 9 0 100 0 2.4 # puctC 改成 2.4
```

> 小样本胜率噪声很大：同一份候选在 16 局里能打出 62.5%，拉到 48 局只有 43.8%。
> 所以**别拿十几局的胜率下结论**，至少几十局、并看 Wilson 下界。


## 已知限制

- 棋力有限（见上文），19 路偏弱。
- 没有让子（handicap）设置，没有棋谱保存 / SGF 导入导出。
- 没有做多线程搜索的结果复现（搜索本身带随机性）。
